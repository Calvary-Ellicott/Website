# Calvary Ellicott website — working notes

Static multi-page church website for Calvary Ellicott (Ellicott/Calhan, Colorado), hosted on GitHub Pages under the church's own GitHub organization. No build step, no server, no dependencies.

## Structure
- Pages: `index.html` (home), `about.html`, `staff.html`, `beliefs.html`, `events.html`, `bulletin.html`, `watch.html`, `connect.html`, `404.html`, plus `update-guide.html` (helper guide, no nav link, `noindex`; its source is `docs/helper-guide.md` and the HTML must be regenerated or hand-updated when the markdown changes). Each page is focused on one thing; the owner chose pages over one long scrolling page.
- Header, nav, and footer markup is duplicated verbatim in every page (no templating). Change it everywhere at once. `scripts/app.js` sets `aria-current="page"` on the matching nav link.
- Inner pages open with a `.page-hero` block (eyebrow, h1, lead). The home page keeps the full-bleed `.hero`.
- An unconfigured ChurchTrac link on any page redirects to `connect.html` and shows the "coming soon" note there via `sessionStorage`.

## Project decisions
- Hosting: GitHub Pages, deploy from `main` branch, root folder (static site, now superseded by WordPress.com, see below). The domain is `calvaryellicott.org` (the `.com` is not registered), registered at Automattic/WordPress.com. On 2026-10-11 its nameservers moved to Cloudflare (root and `www` stay DNS-only records to WordPress.com). `connect.calvaryellicott.org` is the ChurchTrac Church Connect side (ChurchTrac rejects subdomains containing "churchtrac"). The README's GoDaddy/GitHub Pages DNS steps are historical. Full plan and current state: `docs/cloudflare-and-churchtrac.md`.
- Backend: ChurchTrac supplies forms and the events calendar via public URLs only. Those URLs live in `data/churchtrac.json`; `scripts/app.js` reads that file on load. Any key works: `data-churchtrac-link="key"` on an `<a>` opens it in a new tab, `data-churchtrac-embed="key"` on a `<div>` swaps in an iframe. Blank or non-https values show a friendly "coming soon" message.
- All page copy lives in `data/content.json`. `scripts/app.js` fills `[data-content="path"]` elements (string or array of lines; `*text*` becomes `<em>`; `{site.key}` interpolates) and `[data-content-list="path"][data-list-type]` blocks (types: details, cards, paragraphs, beliefs, forms). The HTML keeps the same copy as a fallback; keep both in sync when adding sections. Content is applied before ChurchTrac wiring because the Connect form list is rendered from JSON.
- Dated PDFs: `findDatedFiles(folder, variants, settings)` in app.js sends HEAD requests for today plus the last `weeksBack` Sundays. Bulletin page uses `bulletins/YYYY-MM-DD.pdf` (settings in `bulletin`); Watch page uses `sermons/YYYY-MM-DD.pdf` (handout) and `sermons/YYYY-MM-DD-notes.pdf` (pastor notes) with settings in `watch`. CSP has `frame-src 'self'` and `object-src 'self'` so same-origin PDFs can embed. Expect 404s in the console from the probing.
- Watch page livestream: `data/watch.json` `boxcastEmbed` https URL goes into an iframe in `[data-watch-embed]` with autoplay/fullscreen allowed. BoxCast keeps its own archive of past services inside the player.
- Alert banner: `data/alert.json` (enabled, style warning|info, message, link, linkText, expires YYYY-MM-DD). `applyAlert` prepends `.site-alert` to body and sets `--alert-height` so the fixed header sits below it. Dismissal is per session via sessionStorage keyed by message text.
- Staff cards render from `data/staff.json` (name, role, bio, email, optional photo). Photos are found by convention: `images/staff/<slug-of-name>.jpg` (then jpeg/png/webp), falling back to initials. The browser probes for the file, so 404s in the console for staff images are expected. The placeholder cards in `index.html` only show if the JSON is missing or empty.
- Keep it static. Do not reintroduce a server, admin panel, framework, or bundler. The site owner dislikes the GoDaddy and ChurchTrac site builders and wants hand-written HTML/CSS/JS.
- Security policy is a `<meta http-equiv="Content-Security-Policy">` tag in `index.html`. If you add a new external host (images, embeds, fonts), add it there too or it will be silently blocked.
- Never commit ChurchTrac credentials, API keys, or member data. Only public URLs belong in the repo.
- Preview locally by double-clicking `preview.bat` (runs `tools/preview-server.ps1`, a PowerShell TcpListener static server on port 8080 with HEAD support) or `preview.command` on Mac. `python -m http.server 8080` also works.
- Review policy: ruleset on `main` requires a PR with 2 approvals, code-owner review, dismisses stale approvals, and the `Required approvals` status check from `.github/workflows/required-approvals.yml`, which passes only when both `primo4e` and Pastor Dan (placeholder `PASTOR-DAN-GITHUB-USERNAME` in CODEOWNERS and the workflow) have approved or authored. Repo admins may bypass.

## WordPress theme (current direction)
- On 2026-09-22 the pastor chose WordPress. On 2026-09-23 it turned out the site is on **WordPress.com, Premium plan** (calvaryellicott.org, still "Coming soon"). Premium allows custom theme upload and plugins but not GitHub Deployments or SSH (Business plan only), so the theme is installed by zip upload. The design is being kept, so `wp-theme/calvary-ellicott/` is a custom theme reproducing the static site. Work on the theme going forward; the static pages remain as a reference and are no longer the deliverable.
- Site structure (pastor's spec, 2026-10-11; Events page added 2026-10-23): the public site is **Home, Discover, Visit, Learn, Events**. Everything people do (forms, events/registration, groups, serving, giving, follow-up) lives in ChurchTrac's Church Connect at `https://connect.calvaryellicott.org`; the site links out to it. Theme v1.1.0.
- Theme layout: `functions.php` bootstraps `inc/` (template-tags, post-types, meta-boxes, customizer, setup). Page templates in `page-templates/` are `discover.php` (story = page content, beliefs accordion, staff section switchable via Customizer `staff_mode`: grid from the Staff CPT, link or embed of `connect_staff_url` = `https://connect.calvaryellicott.org/staff`, or off; leaning toward Church Connect but ON HOLD as of 2026-10-19 pending a meeting with the pastor; leave `staff_mode` on grid. Scott wanted the Connect staff page to pull from ChurchTrac People records, which Connect cannot do: Page cards only take static HTML per section, there is no public API), `visit.php` (details, directions, plan-a-visit link), `learn.php` (BoxCast + video archive button, sermons, announcements card linking into Church Connect; bulletins removed 2026-10-23), `events.php` (ChurchTrac calendar embed); `ce_page_by_template()` finds pages by template so links never depend on slugs. `front-page.php` is the homepage with a Church Connect band; copy comes from the Customizer (`ce_opt()` with defaults in `inc/customizer.php`). Church Connect links: `ce_connect_url($key)` / `ce_connect_link()` use `connect_url` plus optional `connect_<events|groups|serve|give|forms>_url`; the nav fallback and Site setup add a Church Connect CTA item.
- Settings: `ce_fields()`/`ce_field_sections()` in `inc/customizer.php` define every theme setting once; `inc/site-settings.php` renders them as a dashboard page (top-level "Site settings", capability `edit_pages`, tabs per section, media picker for images) and the Customizer registers the same list. Staff stays in WordPress (decided 2026-10-23). Since 1.3.0 no template prints literal headings: every eyebrow, headline, paragraph and button label is a setting (the Visit page's Sunday section, the staff heading, the "cards at the bottom" headings per page, etc.), so `ce_next_steps()` takes setting keys, not strings.
- Edit mode (1.3.0, `inc/inline-edit.php` + `assets/edit.js` / `edit.css`): a logged-in user with `edit_pages` sees an "Edit this page" bar (and admin-bar item) on the front end; in edit mode every element marked `data-ce-edit` becomes `contenteditable` (plaintext-only) and Save posts the changes to `POST ce/v1/inline` (cookie auth + `wp_rest` nonce), then reloads. Targets: `opt:<key>` (text/textarea settings only, cleaned by `ce_field_sanitizer`), `post:<id>:title|content|excerpt` (content only for the CPTs, excerpt only for pages), `meta:<id>:_ce_eyebrow|_ce_role|_ce_link_text`. Templates mark text with `ce_edit_attr( target, 'text'|'lines' )` on the element, `ce_opt_span( key )` inside a longer line (ribbon, button labels; `ce_connect_link()` takes a 5th `$label_key`), `ce_post_attr()` / `ce_meta_attr()`; `ce_editing()` is false for visitors so the public markup is unchanged. `lines` format needs the template to print with `nl2br`. Block content stays in the page editor; `ce_editor_link()` prints the way there in edit mode. 1.3.1: key, keypress, keyup and paste events that start inside an editable field are handled by window capture-phase listeners and stopped there, because WordPress.com's single-key shortcuts (e.g. `n`) fired while typing. Saves go live immediately (no review step), so Contributors cannot use it. Client-side flow was verified with a static harness (`wp-theme/dist/edit-harness`, gitignored) served by the static-preview server; the PHP side is unverified until the theme runs on WordPress.com.
- Homepage hero rotates through `hero_images` (newline-separated URLs, picked with a multi-select media control in Site settings; `ce_hero_images()` falls back to `hero_image`, then the stock photo); `.hero-slide` divs crossfade in `site.js` every `hero_interval` seconds, skipped under prefers-reduced-motion.
- Story-style photo panels use `ce_story_image( key )`: `story_image` (home), `discover_image`, `visit_image`, each picked in Site settings; the photo is an `<img>` contained inside the padded panel (not a cover background); empty shows a branded placeholder. No Unsplash hotlinks remain in the theme (1.2.3). `ce_brand()` renders the header/footer brand: the `site_logo` image (Church details tab) or the "CE" mark with the name (1.2.4).
- Custom post types (all non-public, shown by templates): `ce_mission` (title + statement, menu_order, shown on Discover as the Mission and vision band), `ce_staff` (title=name, content=bio, featured image=photo, meta `_ce_role`, `_ce_email`, ordered by menu_order), `ce_belief` (content=statement, menu_order), `ce_sermon` (post date = Sunday, meta `_ce_handout`, `_ce_notes`, content=optional summary), `ce_alert` (title = message, published = shown, meta `_ce_style`, `_ce_expires`, `_ce_link`, `_ce_link_page`, `_ce_link_text`). None of them use the block editor: `inc/meta-boxes.php` disables it (`use_block_editor_for_post_type`) and renders one prebuilt form via `edit_form_after_title`; `_ce_body` textareas save to `post_content` and `_ce_sunday` sets `post_date` through `wp_insert_post_data`. Pages keep the block editor and have `_ce_eyebrow`; the excerpt is the banner lead.
- `Appearance → Site setup` (inc/setup.php) creates Home/Discover/Visit/Learn, sample beliefs/staff (Dr. Dan Hooker, Don Drury), the menu with a Church Connect custom link, and sets the front page; idempotent. Since 1.2.5 a rerun also adds pages missing from an existing menu (Events was added in 1.2.0 after the first menu was built) and keeps the Church Connect link last. Since 1.3.2 the menu also gets an Announcements custom link (class `nav-announcements`, label `announcements_label`, URL `connect_announcements_url`, default `https://connect.calvaryellicott.org/announcements`) just before Church Connect; a rerun adds it to an existing menu when missing, and the fallback nav prints it too.
- `style.css` is the static `styles.css` plus a theme header and a few WordPress-specific rules (menu `ul/li` reset, `.prose` for block content). Keep the two stylesheets in sync if the static site is still touched.
- Scott has WordPress admin as of 2026-10-11. The Editor-only workaround (block markup pasted into the pastor's theme) is archived in `archive/wp-blocks/` with its generator.
- Deploy: `.github/workflows/deploy-theme.yml` ("Theme") lints PHP on PRs and pushes; on push to main it zips the theme and attaches `calvary-ellicott.zip` to a GitHub Release tagged `theme-v<Version from style.css>`. Locally, `tools/package-theme.bat` writes `wp-theme/dist/calvary-ellicott.zip` (gitignored). Install/update = Appearance → Themes → Upload Theme → Replace current with uploaded. No GoDaddy/SSH workflow remains. Local testing: `wp-theme/docker-compose.yml` (WordPress on :8088, theme bind-mounted). No PHP is installed on this machine; lint with Docker `php:8.2-cli`.
- `docs/helper-guide.md` is written for the WordPress dashboard (Contributor role, Submit for Review). `update-guide.html` is regenerated from it by the scratch generator.
- Content review on WordPress uses roles (Contributor/Editor) and optionally PublishPress; the GitHub two-approval rule now only covers theme code.

## Mail portal plugin (wp-plugin/ce-mail)
- Separate plugin at `/mail` for staff: Purelymail inboxes over IMAP/SMTP (per-user login stored encrypted in usermeta `ce_mail_mailbox`), marketing campaigns via Resend Broadcasts + one Audience, ChurchTrac CSV import into `wp_ce_mail_contacts`, campaigns in `wp_ce_mail_campaigns`. Marketing section is hidden and its REST routes refuse unless the `marketing_enabled` setting is on (decided 2026-10-18: mass email goes out from ChurchTrac; Resend stays wired in the background). Preview mode with sample data when no mailbox / no Resend key. Docs: `docs/mail-portal.md`.
- Structure: `ce-mail.php` bootstrap; `inc/class-imap.php` (own TLS IMAP client, literal-aware), `class-mime.php` (headers, multipart, decoding, safe HTML, message builder), `class-mailbox.php` (per-user glue, PHPMailer SMTP send + APPEND to Sent), `class-resend.php`, `class-store.php` (tables, CSV import), `class-rest.php` (namespace `ce-mail/v1`, capability `ce_mail_access`), `class-admin.php` (Mail → Settings), `class-frontend.php` (rewrite `^mail/?$`, renders `templates/app.php`), `assets/app.js` (vanilla SPA) + `app.css`.
- Email admin (0.2.0, 2026-10-23): `/emailadmin` (rewrite `^emailadmin/?$` → `ce_mail=admin`, `manage_options` only, `templates/admin.php` + `assets/admin.js`). `inc/class-purelymail.php` wraps Purelymail's account API (`https://purelymail.com/api/v0/`, header `Purelymail-Api-Token`; token setting `purelymail_token` stored encrypted, `mail_domain` setting). `inc/class-groups.php`: tables `wp_ce_mail_groups` / `wp_ce_mail_group_members`; `sync()` makes one exact-match routing rule per group that has an address (targets = members), replaces it on change, leaves rules it does not own alone. REST routes `ce-mail/v1/admin/*`. No user deletion on purpose. Request shapes came from the Raycast Purelymail extension (Purelymail publishes no API reference); unverified against the live account. Docs: `docs/mail-portal.md`, Sieve notes in `docs/purelymail-mail-rules.md`.
- Mailbox sign-in (0.3.0): `/mail` for a logged-out visitor renders `templates/login.php`; POST `ce-mail/v1/session` checks email+password over IMAP (domain-restricted, throttled) and `inc/class-session.php` keeps them in an encrypted HttpOnly cookie `ce_mail_s` (no DB). `CE_Mail_Mailbox::creds(0)` reads the cookie, so every mailbox route works for guests; `can_market()` and `/emailadmin` still need a WordPress user. Pages render from `parse_request` (`CE_Mail_Frontend::requested()`), not only rewrite rules.
- Package with `tools/package-plugin.bat` → `wp-plugin/dist/ce-mail.zip` (gitignored). Never run on this machine (no PHP, and Docker Desktop crashes on ShadowTablet as of 2026-10-23); `.github/workflows/plugin-lint.yml` lints the plugin's PHP (7.4 and 8.3) and JS on push. First activation on WordPress.com is the real test. Outbound IMAP 993 / SMTP 465 from WordPress.com is unverified.
